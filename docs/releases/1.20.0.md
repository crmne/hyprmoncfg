# hyprmoncfg 1.20.0

Help for displays that won't stay on, honest status for displays without a picture, and more reliable wake-ups. This release works with [panel 2.4.1](https://github.com/crmne/omarchy-hyprmoncfg/releases/tag/v2.4.1) for Omarchy; the panel doesn't need an update.

## Displays that won't stay on get gentler settings

Some displays can't hold the settings saved for them. They drop off a second or two after every connect, over and over, or they come back from sleep turned on but without a picture ([#67](https://github.com/crmne/hyprmoncfg/issues/67)). Retrying the same settings never helped.

Now the daemon steps that display down one setting at a time:

1. VRR off.
2. The next lower refresh rate, for example 144 Hz to 120 Hz.
3. About 60 Hz.

It keeps the first one that sticks. Resolution, scale and position don't change, so nothing else on your desk moves.

What counts as a failure:

- **Dropping:** three connections shorter than 8 seconds within 3 minutes. A single bounce while a display powers up doesn't count.
- **No mode:** two tries in a row that leave the display on but without a mode.

The daemon makes the change while the display is disconnected, so it comes back already in the gentler setting.

Your saved profile never changes. `hyprmoncfg status` says which display was stepped down and how it runs now. The daemon remembers it across restarts. Applying any profile tries the saved settings again.

Two limits:

- **Identical models:** two displays with the same description can't be told apart, so they are never stepped down.
- **A silent black screen:** hyprmoncfg can't see a display that stays connected but shows "No signal". Hyprland and the kernel report it the same as a working one.

## Status counts displays without a mode

`hyprmoncfg status` used to say "4 enabled" when two of those displays had no mode and showed nothing. It now says `4 enabled (2 without a usable mode)`, and still names each one.

## VRR off means off

A profile with VRR off used to leave VRR out of the generated monitor rules. Hyprland then used its global `misc:vrr` setting instead, so if you had VRR on globally, a display set to off got VRR anyway. The generated rules now always say `vrr = 0` for off.

## Waking up after resume or opening the lid

- **Wakes that don't take:** if displays still report being asleep right after you resume or open the lid, the daemon now tries the wake up to three more times. Before, it treated them as asleep on purpose and left them dark.
- **Laptop panel:** if the laptop screen was turned off while the lid was closed and the external display stays asleep after you open it, the daemon turns the laptop screen back on without waiting for the external.
- **Busy Hyprland:** the wake command now uses the right Lua or legacy syntax even when Hyprland is too busy to answer right after resume.

These wake changes come from [#59](https://github.com/crmne/hyprmoncfg/pull/59) by [@Brams-s](https://github.com/Brams-s).

## Upgrading

Update both `hyprmoncfg` and `hyprmoncfgd`, then restart the service:

```sh
systemctl --user restart hyprmoncfgd.service
```

The IPC protocol is still version 1. Status adds an optional `fallback` field for a stepped-down display, and older clients ignore it. The panel doesn't show it yet; `hyprmoncfg status` does.

## What's tested

Automated tests cover:

- the step-down order, what counts as a failure, remembering steps across restarts, and clearing them
- the gentler rule being written while the display is disconnected
- status output
- explicit VRR in every config format
- the wake retries, the laptop screen coming back, and the wake command when Hyprland is busy

None of this has been tried on real hardware yet: no display was power-cycled and no lid was opened. If you saw [#67](https://github.com/crmne/hyprmoncfg/issues/67), please say there whether 1.20.0 brings your displays back.
