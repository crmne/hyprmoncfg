# hyprmoncfg 1.24.1

A fix release for the daemon. Two monitors that come back on each other's display pipe are now recognised, the daemon keeps its hands off your config when monitor management is off, and it no longer gives up when you open the TUI while it starts. Install from the AUR or download a package below. This release works with [panel 2.9.0](https://github.com/crmne/omarchy-hyprmoncfg/releases/tag/v2.9.0) for Omarchy; the panel doesn't need an update.

## Fixed

- **Two monitors stuck on each other's display pipe get a clear fix instead of a lower refresh rate.** With aquamarine 0.15.0, turning two monitors on close together can hand each one the kernel display pipe (CRTC) of the other, and both stay black at `0x0`. 1.24.0 recognised only a pipe left on a disconnected port, so it read this as monitors unable to hold their mode and stepped them down. The daemon now recognises the swap, leaves their settings alone, and logs what clears it: turn one of the monitors off, wait 5 seconds, and turn it on again. It doesn't switch consoles for this case, because on our test desk that didn't clear it and left the text console on screen. aquamarine 0.15.1 fixes the bug itself ([hyprwm/aquamarine#428](https://github.com/hyprwm/aquamarine/issues/428)). See [displays stuck without a mode](https://hyprmoncfg.dev/daemon/#displays-stuck-without-a-mode).
- **Restarting the daemon no longer takes back monitor configuration you handed to Hyprland** ([#93](https://github.com/crmne/hyprmoncfg/pull/93)). After `hyprmoncfg unmanage`, a daemon restart or a reboot put the generated include back into your Hyprland config, so the next reload applied hyprmoncfg's monitor rules again. It now leaves the config alone until `hyprmoncfg manage`. By @jualvarez.
- **The daemon waits for the TUI instead of failing to start** ([#94](https://github.com/crmne/hyprmoncfg/pull/94)). When the TUI or a CLI command was editing monitors directly as the service started, the daemon exited and systemd restarted it every 2 seconds for as long as the editor stayed open. It now logs that another writer is active, waits, and starts as soon as the editor closes. Stopping the service still stops it right away. By @jualvarez.

## Upgrading

Update both `hyprmoncfg` and `hyprmoncfgd`, then restart the service:

```sh
systemctl --user restart hyprmoncfgd.service
```

The IPC protocol is still version 1.

## What's tested

- **Automated tests** cover each fix: the swapped-pipe signature and that it neither switches consoles nor lowers settings, an unmanaged daemon start that leaves the root config untouched and doesn't reload, wake commands that keep the right syntax in that state, and a daemon that waits for the writer lock, takes it when the editor releases it, keeps it exclusive, and stops cleanly while waiting.
- **On real hardware:** an RTX 3090 with an MSI MPG321UR-QD and an LG 16MR70 on DisplayPort, Hyprland 0.56.2 and aquamarine 0.15.0. Turning both monitors on close together left each on the other's pipe. A build that switched consoles for it left the text console on screen, and turning the LG off and on again brought both back, which is what this release advises. The final log message itself has not appeared on hardware yet.
- **Not tried by us:** the unmanaged restart and the writer wait on hardware. @jualvarez tested both on their own machine, combined with another fix, on an earlier base.
